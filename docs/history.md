# History and decisions

A short log of how the project got here, why, and what is still open.

## Timeline

1. **Prototype.** An original play-money skin-game site: cases, case battles, crash, double, plinko, mines, coinflip, upgrade, rewards and levels, daily race, chat, provably fair verifier. Deployed to Vercel.
2. **Vite and TypeScript migration** (PR #1, merged). Tests and CI added. Strict type-checking for the core modules.
3. **Supabase question.** Not needed for the play-money demo; useful for real accounts, server-side fairness, shared leaderboards and chat. Built as an optional backend.
4. **Compliance tooling** (modelled on how skin-gambling operators present these controls): responsible-gambling tools, sandbox KYC and AML, an RNG lab. See [compliance.md](compliance.md). No licence is claimed.
5. **Optional Supabase backend:** schema, row-level security, server-side Crash bets, seed commit and reveal, real daily-race view, chat table, account export and deletion.
6. **Accounts.** First an email/password form, then rebuilt to match the owner's reference screenshots: Log In and Register tabs, Google and Steam, an account overview modelled on a reference profile page.
7. **Login rework (owner feedback):**
   - Top-right **Log in** button, in the site's own style.
   - Google and Steam only: Twitch and Discord removed.
   - No date-of-birth field and no "gambling is allowed where I live" tickbox at sign-up.
   - Signed-out visitors can browse but cannot bet or claim; anything like that opens the popup with a reason. Balance, inventory, seeds and the "You" player disappear while signed out.
   - The Steam profile name is the username, and the Steam or Google picture is the avatar.
8. **Cleanups (owner feedback):** session timer removed from the top bar; the Provably fair banner removed from the home carousel (three slides left); the "Welcome back" bar hidden when signed out.
9. **UX review.** The Vantage reviewer audited the interface from source; every finding was fixed the same day (see [ux-review-2026-11-18.md](ux-review-2026-11-18.md)): opt-in click guard, accessible dialogs and forms, guest cards, phone navigation sheet, carousel pause, motion and contrast fixes, clearer limits and break wording.
10. **Production setup:** Supabase project created, schema applied, Google provider enabled, Steam and account-closing functions deployed, environment variables set on Vercel, site deployed, branch pushed and pull request opened.

11. **Separate cloud accounts (2026-11-20).** The owner noticed three cloud accounts showed one shared balance: cloud mode stored game state under the shared guest key. State and seeds are now keyed per Supabase user. Old shared data is not migrated. Still browser-local: coins, items and seeds do not sync across devices (only Crash settles in the database).
12. **Live multiplayer (2026-11-21).** The owner asked for friends to be able to play battles together. Added `0002_live.sql` (lobbies, seats, secret seeds revealed at the start, realtime), a client data layer, live Coinflip and Battles, real chat and a shared bet/drop feed. The server draws the shared result; stakes stay in each browser (play money). See [live-multiplayer.md](live-multiplayer.md). **Needs the SQL run once in Supabase, and a two-person test on the real project.**
13. **Footer and legal pages (2026-11-21).** The owner asked for the footer and legal pages to follow what three comparable sites publish (Cobalt Lab, Bandit.camp, Clash.gg), with demo information for the firm and the owner. Built a new footer and ten pages in original wording with a fictional operator in `src/company.ts`. While doing it, found that account deletion left names in live games; added `0003_live_erasure.sql`. See [compliance.md](compliance.md). **0003 must be run in Supabase.**
14. **Claims, coinflip bot, bet cap, VS label (2026-11-21).** Owner feedback: (a) the daily and welcome crates could be opened twice by the same user. The limit lived only in each browser's storage, so the same account on localhost and on the live site, or on two browsers, got one crate in each place. For cloud accounts the server now records each claim (`free_claims`, `claim_free()`), the welcome crate is one per account (it was three) and a double click is ignored. Browser-only accounts keep the local rule. Other free rewards (rakeback, login calendar, promo codes, level keys) are still browser-side and have the same weakness. (b) live coinflip regained **Call bot**. (c) the unverified bet cap went from 50 to **1,000** (tier 1 2,500, tier 2 5,000), in `src/kyc.ts` and in `place_bet()`. (d) the battle VS chip was 7 px off-centre and overlapped the left player bar; it is now centred from the grid gap. **0004 must be run in Supabase.**
15. **Shared Crash and Double (2026-11-21).** Owner: the crash had no live data on who bets, and a friend's bet could not be seen on the right; Double the same. Both games ran solo rounds with simulated players, so a friend could never appear. Built `0005_rounds.sql`: one round per game run by the database clock, bets visible to everyone, a secret crash point until the crash instant, server-timed cash-outs, server-applied auto cash-outs, and double payouts by the published rules; plus `src/rounds.ts` and a `LIVE` branch in both pages. See [live-multiplayer.md](live-multiplayer.md). **0005 must be run in Supabase; not yet tried with two real players.**
16. **Admin site, step A (2026-11-21).** After the proposal and the owner's decisions (full scope, full server wallet, separate admin site, Owner only for now, every permission switchable by a higher rank, Steam + authenticator + admin password, read-only data explorer), built the foundation: `0006_admin.sql` and a separate admin site with the three-step sign-in, roles with ranks, editable permissions, an append-only audit log and the Owner's read-only explorer. See [admin-site.md](admin-site.md). **0004, 0005 and 0006 must be run in Supabase and the Owner statement executed; not yet tried with a real sign-in.**
17. **Admin step B1: site controls (2026-11-21).** First slice of "control and visibility". `0007_site_controls.sql` adds one settings row and the guards that the database itself enforces: maintenance mode (with a one-minute warning on the page), a site notice, per-game switches, sign-ups open or closed, and country restrictions read from the connection's country header (compared, never stored). The guard is added to the live games, the free crates and sign-up by editing the stored function text, with a test that calls every entry point; leaving and cashing out are never blocked; staff are never locked out. The game site got `src/site.ts` (notice bar, full-screen messages, paused-game panel); the admin site got a Site controls page. The Privacy page now says the country check exists. Browser-only games (Cases, Upgrade, Plinko, Mines) are paused by the page only until the full wallet (step D). **0007 must be run in Supabase after 0006.**
18. **The server wallet (2026-11-21).** The owner: every game mode must keep coins on the server, not in the browser. Built in two halves. Database: `0008` to `0012` (wallet, inventory, catalogue generated from `src/data.ts`, Cases, Upgrade, Plinko, Mines, Coinflip, Battles with all seven modes ported to SQL, Crash and Double stakes and payouts, faucet, rakeback, calendar, promo codes, free crates, race prize); new accounts start at 0; 67 database tests including a battle-by-battle comparison with the browser's `decide()` and a ledger replay. Page: `src/wallet.ts` mirrors the server, `state.ts` makes `credit`, `grant`, `addItems` and `removeItems` inert while it is on (nothing can be minted from the browser), payouts are held until their animation ends, every game and reward page asks the server, the Cloud account tab re-checks every bet. See [server-wallet.md](server-wallet.md). **0008 to 0012 must be run in Supabase, in order; 0011 closes games that were waiting, without refunds.**
18a. **Owner feedback after the wallet (2026-11-21).** Fixed as the owner tested the live site, each pushed and deployed: a new item now appears in the inventory counter only after its reel animation ends, although it is stored at once (a refresh or the Inventory page shows it); the case-opening animation was rebuilt to feel crisp and smooth (a single velocity curve, whole-pixel positions, a short pause before the winner lights up) and the rarity glow was toned down; the battle VS chip got space; Double betting was redrawn like other sites (the stretched avatar was the problem); the chat no longer flashes simulated players on refresh when a cloud sign-in is saved; the top-bar balance and inventory glow green only for gains (selling, an item added), not for every state event; case opening has one speed plus a lightning "fast open" button (between the old Fast and Turbo, also for demo spins); the "You unboxed" panel was removed; the top-bar level badge follows the account's real level. Also documented and tested how to give coins by SQL (an adjustment ledger line, or a promo code).
19. **Crash pace and the number on screen (2026-11-22).** The owner: the number while rising did not match the number it crashed at (it looked like 1.20 and crashed at 1.03), and it counted too fast. Cause: the database decides a round has crashed only when a browser asks, so the page kept climbing for the time it took to hear (polling plus network, up to over a second). Fix: slower pace (`0013_crash_pace.sql`, `crash_rate()` 0.00008, 2x after 8.7 s), everybody checks four times a second while a round runs, and the number is shown 0.4 s behind the server and never past the last moment the server confirmed the round was still running (`liveElapsed`). Crash timing was deliberately NOT compensated at cash-out: a cash-out judged at an earlier time would let a modified page cash out at almost the crash point every round, because the crash point is published before such a window would close.

20. **The real Counter-Strike 2 catalogue (2026-11-21).** The owner asked for every item of the game, with its picture and price, to replace the invented items in the cases. Names, grades, wear and pictures come from ByMykel's CSGO-API, prices from Skinport's bulk API (lowest listing), joined on the market name: 14,411 priced items. The 27 cases were rebuilt from real skins by theme and value band with the same maths (weight 1/value^1.25 or fixed odds, price = expected value / 0.9, tickets out of 100,000). The owner then asked to check what credit-card deposits pay on comparable sites (screenshots) and apply it: coins per dollar 1.61 and 1.666 (average 1.64); item values are now Skinport USD x 1.64. Only the 166 items inside cases are bundled; the Upgrade page searches all of them from static index and item files (`src/catalogue.ts`). The database got the whole catalogue (0014, five parts) and the cases (0015); old inventory items are swapped for the closest real item. The footer and legal pages no longer say item names are invented. Details: [real-catalogue.md](real-catalogue.md). Open: pictures are hotlinked from Valve's servers; free-coin amounts were not rescaled.

21. **New case art (2026-11-21).** The owner re-made all the crate pictures with ChatGPT (from a folder of the old crates that was prepared for that) so that every case shows the real items it holds, and supplied 27 transparent 1024 x 1024 PNGs, one per case. They replace the old pack: `public/assets/cases/<id>.webp` (640 x 640, converted with `sharp` from `source-art/vault-rush-cs2-filled-cases`, which is not in git). The four cases that used to borrow another crate's picture (10% AWP, 20% Knife, 5% Cosmic, Welcome Crate) now have their own. `src/data.ts` no longer maps cases to pictures (the picture is always `assets/cases/<case id>.webp`), and the old code-drawn crate was removed from `caseArt` in `src/ui.ts` (a missing picture shows a neutral grey tile). The old art pack and the copy prepared for ChatGPT were deleted. The home page "Cases" game tile (`public/assets/home/cases.webp`, 480 x 340) had been a copy of the old Starter Crate; it is now the 5% Cosmic crate (purple and gold, an exotic AK inside), trimmed and fitted to the tile size.

22. **n8n for operator alerts and a daily report (2026-11-21).** The owner asked how to use n8n with the project. It was agreed to keep it out of the game path (money and items stay in database functions) and use it for operator alerts and a morning report. Built `0016_ops_events.sql`: a settings table nobody but the owner can read, an asynchronous sender (pg_net) that never raises, triggers for new players, big wins, coins added by hand, admin actions and maintenance, and `ops_daily_report()`, guarded by the same secret sent in a header so n8n needs only the public key, never the service key. Two importable workflows in `n8n/`. 16 database tests; the workflows were imported and run in a real n8n 2.48 in Docker against a stand-in server (this found and fixed a text-sorting bug in the report's per-game list). Not tested: the real pg_net to n8n hop and real Discord. The Privacy page names the automation service. Setup and details: [n8n.md](n8n.md). The owner then ran 0016, set n8n up on their own PC (Docker Desktop, a gate that lets only webhooks through, a free ngrok tunnel), and both workflows were confirmed end to end on the live site: the test alert and the daily report reached their Discord. Alerts are on in the live database; they only arrive while that PC and Docker are running (the database does not retry). Commit `a20edeb`, deployed.

23. **Documentation rule (2026-11-21).** The owner asked that the documentation and the memory notes are kept up to date constantly, on every addition, change or deletion, and that every related file is updated, not only the history. A full audit of all Markdown files followed: `architecture.md`, `supabase/README.md`, `accounts-and-auth.md` and the root README still described the old state (browser-only game state, only Crash on the server, invented items and 3 speeds); they were corrected, an Assets section was added to `architecture.md`, n8n and picture-replacement sections to `deploy-and-workflow.md`, and the other docs got the notes that concern them (server wallet, admin site, compliance, the admin proposal, the catalogue). The owner then pointed out that `accounts-and-auth.md` called the no-backend mode "the default" although the two Supabase variables are set on the live site and locally, so a new page, [setup-status.md](setup-status.md), lists what is set up, what is set but not confirmed and what is not set, checked against the real project; the "two modes" text was rewritten (cloud mode is what the live site runs) and status notes were added to the docs of each feature. The check also found that **GitHub CI runs only on pushes to `main` and on pull requests, so nothing since PR #2 has been checked by CI**, and that maintenance mode is off and both Steam functions are deployed. The owner chose to fix the CI gap by running CI on every branch: the workflow's `push` trigger now covers all branches, with a cancel-in-progress rule so a newer push replaces a run still going.

## Decisions worth remembering

- **Play money only, and honest about it.** Simulated parts are labelled as simulated. No real-money paths.
- **The site's own design wins** over copying a reference site. References were used for structure and features.
- **Age is a tickbox at sign-up;** stronger checks are the opt-in sandbox verification. The database still refuses a profile without the adult flag.
- **Two gates, not one:** `debit()`/`grant()` refuse when signed out, and a click guard explains why. Both matter.
- **Signed-out state is blank and never saved,** so nothing personal can leak into a logged-out view and no data is created for visitors.
- **Steam via an Edge Function** because Supabase has no Steam provider; Google via Supabase's own provider.
- **Secrets stay out of the site and the repository.** Only the publishable key is in the browser.
- **Docs and memory are kept current on every change.** Update every related document in the same piece of work (see the ground rules in [README.md](README.md)).
